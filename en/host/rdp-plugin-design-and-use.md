# RDP plugin: design and use

中文: [RDP远程桌面插件设计与使用](../../zh/host/RDP远程桌面插件设计与使用.md).

`velashell.rdp` is an in-process workspace plugin in [velashell-plugins](https://github.com/VelaShellLabs/velashell-plugins/tree/main/plugins/VelaShell.Plugin.Rdp). It renders a remote desktop inside an Avalonia tab on Windows, Linux and macOS. The engine is a **pure-managed C# RDP client** — no FreeRDP, no bundled native binaries — shipping one managed assembly for every RID.

## Architecture and scope

The protocol stack is the standalone C# library `VelaShell.Rdp` (MIT, released with the repository): it is UI-agnostic, does not depend on the plugin SDK, and implements the subset of MS-RDPBCGR / MS-RDPELE / MS-RDPECLIP / MS-RDPEDISP / MS-RDPEFS this plugin needs. The plugin references the library, whose DLL ships inside the plugin's signed `.vpx`; it is not published as a separate NuGet package. Layers:

- **Wire** — TPKT/X.224 framing, fast-path frames, ASN.1 PER/BER.
- **Security** — TLS via `SslStream` (OS trust, or an exact SHA-256 leaf-certificate pin); NLA/CredSSP via `NegotiateAuthentication` (NTLM + the TSRequest public-key binding).
- **MCS/GCC** — Connect-Initial/Response, erect/attach/channel-join.
- **PDUs** — client info, licensing, capability exchange, connection finalization.
- **Graphics** — interleaved-RLE decode and MPPC bulk decompression, a BGRA framebuffer; fragmented fast-path updates are reassembled.
- **Input** — fast-path keyboard/mouse/Unicode.
- **Channels** — clipboard (cliprdr) and drive mapping (rdpdr) over chunked static virtual channels; the dynamic virtual channel (drdynvc, MS-RDPEDYC) opens only the Display Control channel (MS-RDPEDISP) to negotiate dynamic resolution, and declines every other dynamic channel (audio, the GFX graphics pipeline) so the server keeps to the classic bitmap path.

The library's `RdpManagedSession` implements the `IRdpSession` / `IRdpClipboardTransport` contracts through an SDK-agnostic `ConnectAsync(RdpClientOptions, …)`; the plugin references the library, supplies the desktop view, input queue and clipboard bridge/codec, and maps the host's connect request to the library's `RdpClientOptions` while translating the library's exceptions into the host protocol exceptions. The host owns connection forms, credentials, certificate approval, session tabs and optional SSH jump transport; the plugin supplies the workspace and remote desktop. Connection, event pumping and teardown run asynchronously on the session worker task, interrupted by a cancellation token. The engine runs in-process and shares the host crash boundary; this is not process isolation or a filesystem sandbox. See [the SDK reference](../sdk/sdk-reference.md), [developer guide](../templates/dev-guide.md) and [current trust boundaries](../plugins/12-security-threat-model.md).

Implemented scope: desktop resolution that follows the window (dynamic resolution), fit/actual-size display, keyboard/mouse/Unicode input, the [remote-keys floating button](#remote-keys-floating-button) (Ctrl+Alt+Delete and other combinations the local OS keeps, plus typing the clipboard), in-view reconnect when a session drops, text/image/file clipboard, directory transfers and mstsc-style drive mapping (tick local disks or list custom folders). It does not negotiate audio, multiple monitors or drawing-order acceleration (RemoteFX/GFX); the server renders via classic RLE bitmap updates, with MPPC stream compression on weak links to cut bandwidth.

## Connect and use

Install the signed `velashell.rdp-<version>.vpx` from the plugin release using the host plugin manager, then create an RDP connection. Supply server, port (3389 by default), username and password. The optional domain is separate from the username. Choose an existing SSH session in **SSH jump host** when needed; the host manages the tunnel and the original destination remains the certificate identity.

| Setting | Default and accepted values |
| --- | --- |
| Domain (`domain`) | Empty; optional domain |
| Desktop width (`width`) | 1920; 320–8192 (initial size and fallback; follows the window once connected) |
| Desktop height (`height`) | 1080; 200–8192 (initial size and fallback; follows the window once connected) |
| Connect timeout (`timeout`) | 15 seconds; 1–120 |
| Security layer (`security`, advanced) | `auto` (default); `nla` NLA only; `tls` TLS only — see [Authentication and certificate policy](#authentication-and-certificate-policy) |
| Bidirectional clipboard (`clipboard`) | `false`; explicit opt-in for text, images and files |
| Local disks (`drive:<disk>`, **Drive mapping** page) | One checkbox per local disk, all unchecked by default |
| Custom folders (`drives`, **Drive mapping** page) | Empty; `name=absolute-path`, several separated by semicolons |
| SSH jump host (`jumpSession`) | None; host SSH-session selector |
| Trusted SHA-256 (`trustedThumbprint`) | Hidden setting supplied through certificate approval; exact leaf pin |

The remote desktop follows the workspace tab: on connect, and once a window resize settles (350 ms debounce), the plugin asks the server over the Display Control channel to match the desktop to the viewport in device pixels, so **Fit desktop** renders 1:1 and crisp. `width`/`height` are the size used on connect and the fallback when a server declines dynamic resize; then **Fit desktop** scales the mismatched framebuffer into the available area (high-quality interpolation) and **100%** shows actual pixels with scrollbars. Use **Ctrl+Alt+Delete** in the toolbar to send that sequence remotely. When a session drops, a **Reconnect** button appears over the desktop (the host session tab reconnects too); reconnecting renews credentials and certificate approval, and a failed attempt keeps the current view so the button stays usable.

### Remote-keys floating button

The plugin installs no global keyboard hook, so combinations the local OS takes first never reach the remote when pressed: Ctrl+Alt+Del is always handled locally, Win+L locks this machine, Ctrl+Shift+Esc opens the local Task Manager, Alt+Tab switches local windows, Win+R / Win+D go to the local Explorer, a lone Win opens both Start menus, and on Windows 11 PrintScreen opens the local Snipping Tool by default. These keys live in the **remote-keys floating button** on the desktop edge:

- At rest it is a semi-transparent circle, docked to the right edge by default. Drag it and it snaps to the nearer left or right edge, keeping its height.
- Its outline uses the theme accent (`VelaAccent`, which follows the user's custom accent colour): on hover the accent ring fades in with a halo growing outwards; opening it turns the keyboard icon away into an ×, which turns a further quarter on hover over a translucent accent fill; buttons in the fan grow 8% and light their accent ring on hover.
- A click fans the actions out on two semicircles facing inwards over a dimmed desktop. The inner ring holds the most used: Ctrl+Alt+Del, Task Manager (Ctrl+Shift+Esc), Switch window (Alt+Tab), Type clipboard; the outer ring holds the Windows keys: Start (Win), Run (Win+R), Desktop (Win+D), Lock (Win+L), Screenshot (PrintScreen). Clicking one sends it and folds the fan.
- Esc or a click on the dimmed desktop folds it; that key or click does not reach the remote. In small views the whole fan (buttons and labels included) scales down, to 0.6 at least, so labels never overlap.
- **Type clipboard** reads the local clipboard text through the SDK clipboard capability (never logged) and types it into the remote: runs of text as Unicode, line breaks as Enter, tabs as Tab. It is meant for the sign-in screen, UAC prompts and consoles, where clipboard sharing does not work. Text with line breaks or over 100 characters is first explained in the status bar and needs a second click on the same text (line breaks are sent as Enter, which runs commands in a console); over 2000 characters it is not typed.
- The former 36px toolbar held only the Ctrl+Alt+Delete button and is gone; the remote desktop gets the full height above the status bar.

### Clipboard and file transfer

Clipboard sharing is off by default. Once authorized, ordinary Ctrl+C / Ctrl+V is used; text and images still synchronize automatically, without Send/Receive buttons.

- **Windows remote→local:** remote Ctrl+C publishes only file/directory descriptors through OLE. Pasting in the chosen local Explorer directory requests indexed IStream content; RDP FILECONTENTS reads start only on those requests. Explorer selects the destination and writes files. There are no global key hooks, destination inference, or prefetched download cache.
- **Local→remote:** focus, activation and remote Ctrl+V publish formats and name/size metadata. Enumeration and safe source-handle preparation read no file content. The remote shell requests FILECONTENTS on paste and owns its destination directory. Ctrl+V still waits for the format-list ACK; descriptor-only preparation shows Ready with zero transferred bytes.
- File descriptors in both directions carry FD_SHOWPROGRESSUI (0x4000, MS-RDPECLIP 2.2.5.2.3.1, as FreeRDP sends), so the receiving Windows Shell shows its own copy-progress dialog; without it a large paste gives no feedback in the destination Explorer and looks hung. Whether the copy runs in the background and the destination Explorer window stays usable meanwhile is the receiving Shell's choice: remotely it depends on the server's rdpclip data object; the local data object implements IDataObjectAsyncCapability, which lets Explorer extract in the background. The plugin's status-bar progress is shown as before.
- Uploads and downloads share the existing **fixed 24px resolution bar**: each direction is one group on the right — direction · transferred/total size · current file name, a 3px progress bar, the state (a percentage while transferring, otherwise the state in words, coloured by state), and the host transfer panel's 10px “×” cancel button (shown only while the transfer can still be cancelled). Idle, one-way and simultaneous transfers never change desktop viewport height. When space runs short the file name trims first, then the state text; the bar and “×” are never pushed out. The tooltip gives exact byte counts and the full state. Publishing a source shows “Available to paste”. Once all unique byte ranges are provided, “File contents delivered/sent” is a terminal state requiring no further wait; its tooltip explains that the destination has not reported the copy result. It does not confirm disk persistence. Uploads have no final remote copy acknowledgement; sources with no content bytes become sent after their descriptors are successfully sent. Only successful local Shell EndOperation with copy/move effects or nonzero Paste Succeeded shows “Copy completed (Shell confirmed)”; ordinary DropEffect/TargetCLSID does not confirm completion. Empty files, directories and EOF require no extra content blocks; without feedback, delivery can remain the terminal state. Failure/cancellation remain distinct, a new operation resets progress, and late progress cannot revert a terminal state to transferring. Completing status never releases consumer-owned IStreams.
- A new copy or ownership change retires the publication; acquired streams retain independent leases. Negotiated CAN_LOCK_CLIPDATA, LOCK/UNLOCK and FILECONTENTS clipDataId retain remote source versions. Peer locks likewise preserve local source handles across new copies. Retired versions unlock after streams and their data object finish or are released; a still-published version remains available for repeat pastes. Explicit cancellation, disconnect and view disposal cancel active streams. Without peer locking, remote source replacement cannot be preserved. Provider failure or process exit may still fail locked transfers; closing a source Explorer window still needs live verification.
- A sent file-block request waits 30 seconds for its response. Only response timeouts get up to two additional attempts, with cancellable 500/1000ms delays. Retries preserve the source version, file index, offset and length, use fresh streamIds, and discard late responses. The existing bar shows Retrying; only successfully delivered unique ranges count toward progress. Explicit CB_RESPONSE_FAIL has no transient classification and is not retried; neither are send errors, cancellation, disconnect or unlocked source replacement. TCP already provides reliable delivery: server rejection is not evidence of packet loss. There is no reconnect resume, whole-file retransmission or duplicate destination write.
- Only unlocked local upload handles expire after 30 idle seconds and are prepared again on the next remote paste. Neither direction creates plugin disk caches, staging or temporary files, or accumulates whole files in memory. Native IStream fills the destination application's buffer in chunks of at most 256 KiB. Progress counts bytes obtained/provided by the plugin, not confirmed destination writes. A partial file not appearing does not prove caching, nor establish that Explorer waits for the whole stream before creating it. Destination creation, refresh, partial-file cleanup and any destination application's temporary files are outside plugin control. Older DataDirectory/rdp-clipboard caches remain untouched because existing consumers may still reference them.
- **Linux/macOS:** this Avalonia integration has no supported remote virtual-file provider. The status bar explicitly reports that remote file paste requires Windows. It neither downloads automatically nor substitutes a manual receive button. Text/images and lazy local→remote files remain supported.

Avalonia 12.1.4 supports delayed values through `DataTransferItem.Set(format, Func<T>)`, but its public file format is `IStorageItem`; application format identifiers are transformed and cannot express native `FileContents` with `FORMATETC.lindex` and `TYMED_ISTREAM`. A separate `WindowsVirtualFileClipboard` therefore supplies OLE `IDataObject`, `FileGroupDescriptorW`, indexed streams and copy drop effect. Its dedicated STA pumps messages; stream waits do not block Avalonia UI or the RDP receive pump. Teardown never calls OleFlushClipboard, which could force content materialization. Ownership checks use OLE identity and the clipboard owner window; sequence checks prevent publication from overwriting a newer local copy. Delayed rendering can itself change the sequence without changing ownership.

OLE accepts DWORD Performed DropEffect, Logical Performed DropEffect and Paste Succeeded feedback, plus the 16-byte TargetCLSID. Successful SetData copies feedback and honors STGMEDIUM ownership: it releases the medium only for fRelease=true; rejected media remain caller-owned. Feedback does not imply EndOperation or close consumer streams. Successful EndOperation releases the operation lease while streams retain independent leases; failure cancels extraction. This fixes the former behavior where every accepted feedback prematurely ended the operation and disposed streams. Ordinary DV_E_FORMATETC / DV_E_DVASPECT probes return PreserveSig HRESULTs directly without throwing a managed COMException each time. Required-format failures remain errors, distinct from explicit remote FILECONTENTS rejection. CLIPBRD_E_CANT_OPEN gets up to eight attempts with bounded asynchronous backoff. Each publication retry rechecks the clipboard sequence, and virtual publication avoids reading back its own clipboard.

Version LOCK is sent before requesting descriptors; clipDataId=0 is a valid ID, distinct from omitting the field, and LOCK has no protocol ACK. Under [MS-RDPECLIP file-content request processing](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpeclip/d19de33e-4027-43de-b150-668ee21bced8), a request carrying clipDataId must read that locked version; an unsatisfied request returns CB_RESPONSE_FAIL without an internal reason classification. Low-sensitivity diagnostics record operation, streamId, lindex, offset, requestLength, attempt, responseFlags, lockCapability, clipDataId, timeout/retry and LOCK/UNLOCK or late-response events where applicable, without file content or credentials. Correlate requests and failures by streamId, then inspect the version lifecycle by operation/clipDataId. Existing field logs do not establish the server provider's internal rejection reason; the reproduced local feedback lifecycle defect cannot be called the sole cause of the reported failure.

FORMAT_DATA_RESPONSE has no wire request ID; the locally attached format number is not an independent response identity. Cancellation, timeout or ambiguous send failure retains the original slot. A subsequent receive waits cancellably for the old response to drain before starting a new LOCK or descriptor request, so late replies cannot satisfy a newer request. A 30-second drain timeout explicitly stops clipboard sharing for that connection until reconnect. Versioned format notifications skip obsolete queued entries; late replies no longer enqueue another receive, and repeated receives of an already published file version do not fetch descriptors or contents again. Shutdown atomically sets stopping before cancelling waits and streams. It starts no further LOCK, descriptor request or clipboard publication, awaits workers and registered version releases, sends at most one UNLOCK per LOCK, and concurrent disposal calls await the same cleanup task. A new Ctrl+C still retires only the publication and preserves acquired stream leases; explicit shutdown cancels all streams. Normal cancellation produces no operation-failed warning, while actual rejection, timeout and loss of response synchronization retain diagnostics. Debugger first-chance OperationCanceledException can represent normal cancellation; a host Infrastructure message without a stack is insufficient to diagnose another defect.

Limits remain 16 MiB per payload, image edges ≤8192 and decoded pixels ≤16 MiB, 4096 descriptors and 1 GiB total file size. Traversal, unsafe names, case collisions, file-as-parent conflicts and symbolic links are rejected while preserving directory structure. Clipboard sharing is independent of drive mapping and the host SFTP queue. File blocks are at most 256 KiB and use 1600-byte channel frames with per-frame send locking; bounded receive queues fail clipboard sharing explicitly on overflow.

Focused local tests cover zero content reads on copy, request-driven transfer, bounded large Read calls, directories/multiple files, pending streams surviving replacement, version locks/unlocks, explicit cancellation/disconnect/disposal, OLE feedback, busy retries and fixed status-bar geometry. Windows tests call actual COM vtables for IDataObject HGLOBAL descriptors and IStream read/seek/release without replacing the user clipboard or pasting to user directories. No public RDP server was contacted; live Explorer-to-RDP end-to-end paste still needs field validation.

### Drive mapping

The connection dialog's **Drive mapping** page follows mstsc's *Local Resources → Drives*: one checkbox per local disk. On Windows every drive letter is listed, labelled by type — "Local Disk (C:)", "Removable Disk (E:)", "Network Drive (Z:)", "CD/DVD Drive (F:)"; on Linux / macOS the root (`/`), the home folder (`~`) and mounts under `/media`, `/run/media`, `/mnt` and `/Volumes`. All are **unchecked by default**.

Disks are enumerated from drive letters and types (or mount points) only — no media access, no volume query — so a disconnected network drive or an empty optical drive cannot slow plugin activation. Every 5 seconds the plugin checks the set of disks and re-registers the connection form only when it changed (with the same provider instance: open remote-desktop tabs are unaffected, and a dialog being edited keeps what was typed), so a USB disk plugged in later appears the next time the connection dialog opens. A ticked disk that is absent at connect time (USB unplugged, network drive offline) is skipped, not an error.

**Custom folders** on the same page share a single directory: enter `name=absolute-path`, separating several with **semicolons** (the host renders text settings as a single-line box, so there are no newlines). Examples: `work=C:\Work\Share;docs=D:\Docs` on Windows, `work=/home/alice/share` on Linux, `work=/Users/alice/share` on macOS. Line-separated values saved by earlier versions are still read. The always-visible hint under the box shows the format with examples for the current OS (the placeholder disappears as soon as anything is typed, so the examples live in the hint); a wrong entry fails the connection with a message that quotes that entry and the correct format, names a clashing name, or states the 32-mapping limit.

Names must be unique, and must not clash with a ticked disk's name (`C`, `E`, `root`, `home`, …); they contain **1–8 ASCII letters, digits or underscores**, hyphens not allowed. Disks and folders together allow at most **32 mappings**. Directories must already exist. The remote Windows desktop reaches a mapping as `\\tsclient\<name>`; an xrdp session at `~/thinclient_drives/<name>`. Each mapping grants remote **read/write access** to that disk or folder; nothing beyond the ticked disks and the listed folders is shared — no home directory, system disk or removable drive. Paths are confined to the mapping; traversal and symbolic links are rejected. Mapping a disk or directory and sending files through the clipboard are separate choices.

## Authentication and certificate policy

The security layer follows `security`: **Auto** (default) offers both TLS and NLA and lets the server choose (a server that supports NLA picks it); **NLA only** requires the server to select NLA and never falls back; **TLS only** offers TLS alone — the credentials travel in the Client Info inside the validated TLS channel and the server performs the logon itself (as when the server's "require NLA" setting is off). TLS 1.2 minimum; legacy RDP security and blanket certificate-ignore are disabled, and certificate validation is identical in every mode. Without a pin, verification uses OS trust plus server purpose, validity and hostname/IP, performed by .NET's `SslStream` against each platform's OS trust store.

**How NLA authenticates.** On **Windows, NLA/CredSSP uses the OS's native SSPI Negotiate package**, exactly like Windows' own RDP client: called with a null target it produces a full SPNEGO token (NTLM/Kerberos) rather than bare NTLM — a hardened server that requires NLA rejects bare NTLM with `0x80090302` (SEC_E_UNSUPPORTED_FUNCTION). Other platforms fall back to managed NTLM (`NegotiateAuthentication`), which still works against servers that accept bare NTLM. The public-key binding (the SHA-256 nonce binding for v5+, the echo for v<5) and the TSRequest envelope follow MS-CSSP and are provider-independent.

**Auto-mode fallback.** If the server refuses right after the client's first CredSSP message — which is only the NTLM NEGOTIATE, carrying no user name and no credential proof — by answering with `errorCode` 0x80090302 (SEC_E_UNSUPPORTED_FUNCTION) or by aborting the TLS session (seen locally as SChannel 0x80090304 "The Local Security Authority cannot be contacted"; one server alternates between the two for byte-identical messages), it does not accept incoming NTLM. That is server policy, not a credentials problem. Auto then **reconnects once offering TLS only**, with the same certificate validation, and logs a warning in the plugin log. If the server refuses TLS too (RDP_NEG_FAILURE `HYBRID_REQUIRED_BY_SERVER`), it requires NLA yet refuses NTLM: the error says this is a server-side setting unrelated to the user name and password and gives both fixes — allow incoming NTLM on the server (Local Security Policy › Security Options › "Network security: Restrict NTLM: Incoming NTLM traffic" = Allow all), or turn off "Allow connections only from computers running Remote Desktop with Network Level Authentication". A wrong password (rejected after NTLM authentication) is still reported as an authentication failure and **never** triggers the fallback.

**Diagnosing connection failures.** Errors name the failing stage (TCP, security negotiation, TLS, NLA, MCS, logon, licensing, capability exchange) and the cause chain, including SChannel / socket error codes; failures after the TLS handshake also name the negotiated TLS version. When the server rejects the logon during NLA, its status code is turned into a specific reason (wrong user name or password, password expired, account locked or disabled, remote sign-in not allowed). When a **session is established and then dropped by the server** (a Set Error Info PDU, MS-RDPBCGR 2.2.5.1.1), its errorInfo code is turned into a reason shown in the disconnect overlay and the status bar: the user was signed out, another connection took over the session, the server denied it or the account lacks permission, an idle/logon timeout, no Remote Desktop licence available (expired RDS licensing or grace period), and so on; other codes fall back to a neutral description plus the hex code. The disconnect log also records **whether a logon notification arrived first** (the server's Save Session Info PDU): if it did, the credentials were accepted and a Windows session started, so the drop is the server ending an established session (usually policy) rather than an authentication or protocol failure; if it did not, the connection never reached logon. The plugin log (`velashell.rdp`) records every failure with the full exception; failures after the TLS handshake add the cipher suite and the headers of the TLS records the server sent (type and length only, e.g. `Alert 26 B` — no payload is ever kept), which tells a server-side abort apart from a local decryption problem.

A host-approved pin is the exact SHA-256 hash of the leaf certificate's DER bytes (64 hexadecimal characters). **Pinning replaces CA/name/expiry validation** with a constant-time comparison of the leaf identity; it is not an additional condition layered onto those checks. A different leaf is rejected and requires a new explicit trust decision. SSH forwarding does not change the expected server name to loopback. Passwords go through APIs, never command-line arguments. NLA/CredSSP uses .NET's `NegotiateAuthentication` for NTLM and message sealing, with the TSRequest public-key binding per MS-CSSP.

## Building and independent delivery

The repository stays on .NET 11 and its SDK/Avalonia settings without changing dependencies. **Managed build only — there is no native step:**

```bash
dotnet build plugins/VelaShell.Plugin.Rdp -c Release
dotnet build plugins/VelaShell.Plugin.Rdp -c Release -t:PackVpx
```

The one platform-specific touch is `UnixClipboardFile`, which P/Invokes the OS `libc` (`open`/`fstat`) to open a clipboard file for local→remote transfer with `O_NONBLOCK|O_NOFOLLOW` (so a FIFO cannot block the open and a symlink is refused); Windows uses the .NET file API. The system libc ships with the OS and is not a bundled native library.

There is no longer an `rdp-native` workflow, CMake, bundled OpenSSL/VC runtimes or six platform native jobs: the plugin ships as **one managed `.vpx`** for every RID. CI and release run managed tests and packaging only. See the [plugin build README](https://github.com/VelaShellLabs/velashell-plugins/blob/main/plugins/VelaShell.Plugin.Rdp/README.md) and [packaging and signing](../templates/publishing.md).

## Verification and remaining boundaries

The locally identified large-file stalls came from holding the publication lock throughout a download, putting focus publication in the keyboard/mouse queue, and holding the send lock for an entire virtual-channel message. Silent cliprdr queue drops and swallowed worker exceptions could also leave requests unanswered. Focused regressions cover local publication while a large-file response is pending, cancellation of pending content requests without creating a local cache, progress bytes and out-of-order retries, workspace status/cancellation/frame refresh, focus publication independent of input, input between fragments with same-channel message ordering, and explicit queue-overflow failure. DriveCapability v2 DeviceData now uses UTF-16LE while the eight-byte PreferredDosName remains ASCII; exact packet tests cover three name lengths. Acceptance of that drive announcement by a real Windows server remains unverified. No public server was contacted for this large-file fix; real Windows bidirectional large-file transfers and slow-network behavior still require field verification.

Outgoing clipboard channel fragments honor the negotiated `SHOW_PROTOCOL` option. Incoming fragments use the `CHANNEL_PACKET_*` flags and the connection's shared MPPC history for decompression before reassembly and clipboard parsing. Without long format names, ASCII registered names use the 32-byte short-name field to preserve `FileGroupDescriptorW`. Local regressions cover compressed format-list acknowledgements with empty payloads, fragmented compressed file descriptors, long/short names and bidirectional file requests. The previous implementation parsed compressed acknowledgements as raw PDUs; parsing failed and publication subsequently timed out. This failure path was reproduced locally. Bidirectional file Ctrl+C/V still requires verification against a real Windows server; without a server channel capture, its reported timeout cannot conclusively be attributed to compressed acknowledgements.

Unit tests cover settings, the clipboard codec, the headless UI and the CredSSP/NLA ASN.1 encoding. Live interoperability tests are gated on `VELA_RDP_TEST_TARGET` (skipped in CI) and exercise the full stack against a real server:

- TLS negotiation and leaf-certificate pin trust; without a pin a self-signed certificate is rejected and its SHA-256 is surfaced for the host trust flow.
- Desktop rendering: interleaved RLE **and MPPC bulk compression** (with the server's `bulk_compression` enabled, compressed PDUs decompress pixel-exact).
- Keyboard/mouse/Unicode input; text and image clipboard round-trips; drive mapping — ticked disks read remotely (including a listing of the system drive root `C:\`), custom-folder read and write.
- **Dynamic resolution**: a resize over the Display Control channel, validated as a 1024×768 ⇄ 1280×1024 round-trip; the framebuffer and status bar follow the reactivation.
- **In-host rendering**: the real `RdpWorkspaceView` and `RdpDesktopControl` render the engine's frames through Avalonia's headless Skia pipeline — the same control tree the host loads; the view is observed to resize the remote desktop to its viewport.

Besides offline ASN.1 tests, NLA/CredSSP is verified live against the FreeRDP shadow server (`/sec:nla`, gated on `VELA_RDP_TEST_NLA_TARGET`): **both the native SSPI (SPNEGO) path and the managed NTLM fallback reach the desktop** (both are exercised on Windows); a wrong password reported as an authentication failure without fallback; TLS only refused by an NLA-only server with `HYBRID_REQUIRED_BY_SERVER`. The security-layer fallback and a first NLA reply that is a refusal (error code or TLS abort) are covered by in-process fake-server tests; every TLS 1.2 cipher suite a Windows server may pick (ECDHE/RSA × AES-GCM/AES-CBC) was exercised against xrdp. On real Windows servers, the behaviour of one that refuses incoming NTLM was confirmed (0x80090302 or a TLS abort on the first message); **a successful NLA logon against a real Windows server is still outstanding**. Interleaved-RLE / MPPC decode, MCS/GCC, capability exchange and the channel wire formats follow MS-RDPBCGR and the related published specs. These checks are not an all-platform or real-Windows-endpoint certification.
