# 10 · 打包、签名与分发

> **发布操作手册见 [publishing.md](../templates/publishing.md)**(编译 → 打包 → 签名 → 提交商店);
> 插件商店:<https://market.easilynet.top>。宿主插件管理已支持**浏览、搜索、详情及直接安装**,
> 也保留本地 `.vpx` 安装与已安装插件更新。下方实现注记与 §4 说明当前能力;其余章节保留长期蓝图。
>
> **实现注记(2026-08)**:本篇的**打包与签名**已落地,**分发(插件源 / 商店)仍按分期推迟**。
> 与下文蓝图的三处出入,以实现为准:
>
> 1. **`.vpx` 是专属容器**,不是"zip 改后缀":64 字节头部(魔数 `56 50 58 1A` + 格式版本 +
>    标志位 + 载荷长度 + SHA-256 + 掩码随机数 + 头部 CRC32)+ 掩码后的 zip 载荷 +
>    可选签名尾。见 `VelaShell.PluginSdk/Packaging/VpxContainer.cs` 与
>    [dev-guide.md §12](../templates/dev-guide.md)。
> 2. **签名算法改为 ECDSA P-256 + SHA-256**,不是下文写的 Ed25519 —— Ed25519 不在 BCL 里,
>    引第三方库会破掉"契约程序集零重量级依赖"这条纪律(那个程序集是宿主与插件唯一共享的类型来源)。
>    签的是 64 字节头部,而头部含载荷长度与摘要,等价于对全包签名。
> 3. **签名不是强制的**:第一方/自装插件场景下"信任即安装"(与 06 的权限系统决策一致)。
>    未签名默认放行,**坏签名一律拒装**;要收紧就打开
>    `PluginManagerOptions.RequireTrustedPackageSignature` 并配 `TrustedPackageKeys`。
>    下文的三档信任标、TOFU、密钥连续性与吊销列表都属于"开放第三方生态时"的未来工作。
>
> **实现注记(2026-09-11):宿主已内置只读商店客户端。** 打开插件管理页时问一次商店
> 「我装的这几个插件有没有新版」,有新版可在页内直接下载安装。与下文 §2 / §3 的出入:
>
> - **没有静态签名索引**(§3 阶段 A)。宿主问的是 `GET /api/plugins/latest?ids=…&pre=`,
>   按 id 批量取最新已发布版本 —— 插件多起来之后,让每个客户端为看几个插件去下整张表,
>   两头都在做无用功;按 id 问,请求规模只跟本机装了几个插件有关,与商店有多大无关。
> - **不做后台定时检查**(§2 写的「默认每日」)。只在用户打开插件管理页时问那一次,
>   不在启动时、也不在后台定时 —— 理由见宿主仓库的 `PRIVACY.md`,那份文件逐条交代
>   每一个出站请求,新增一条就得写进去。
> - **默认不吃预发布**:接口有 `pre` 参数,宿主一律不传。想装 beta 走 `vela-plugin --pre`。
> - **自动更新仍然不做**(与下文一致)。但「发布者没变就直接装」是做了的:指纹与安装时钉住的
>   那一个对得上就不再多问一句;换了人、或者这一版干脆没签名,则走完整确认流程。
> - **降级没做**(§2 末条):本机不留上一版缓存。
> - **宿主太旧装不上的新版:给提示、不给按钮** —— 兑现 [03 §7](03-plugin-model.md) 那句
>   「在插件管理页给出明确的需升级宿主提示」。摆一个按下去必然失败的按钮比不摆更糟。
> - **升级不再清插件数据**:覆盖安装走「停用 → 换目录」,KV / 机密 / 时序一律留着,
>   只有卸载才清 —— 与 `vela-plugin update` 一直以来的行为对齐。

> **当前集成补充：**「已安装 / 插件商店」双页签，商店进入时才发起匿名
> `GET /api/plugins/?q=…&sort=…&page=…&size=20`，选择条目调用 `GET /api/plugins/{id}`。
> 支持搜索、最近更新/下载量/评分排序、分页、详情重试及最新稳定版安装；没有多源聚合、分类筛选、
> 版本历史选择或回退。详情 Markdown 禁用 HTML 与图片，仅允许点击 https 链接。
> 点安装后才取下载票据；https、整包 SHA-256、包签名和发布者变更确认沿用现有安装管线。
> 覆盖旧版前还会核对包内 ID、版本与实际兼容要求；失败保留旧版。进度可见、下载可取消，
> 「全部更新」取消后停止后续下载。浏览与下载的外发字段已同步宿主 `PRIVACY.md`。

> **临时安装产物的生命周期（1.8.0）：** 下载包的租约持续到校验、发布者确认与安装完成；取消或失败在释放租约前删除包与半截下载。解包暂存继续放在用户插件根下，保留同文件系统原子换目录；开发影子副本在管理器存活期间持有租约。启动清扫只回收命名匹配、带所有权标记且可取得排他租约的遗留产物。未标记的旧版缓存无法证明无人使用，保守保留。升级备份仅在目标缺失、恰有一个结构有效的候选时恢复，再走正常信任验证；有歧义或可能承担恢复用途的备份不作为垃圾删除。新建备份带有 `.owned` 所有权标记，安装与回收共用插件根的 `.install.lease` 排他租约；新目标结构有效、受保护且非补录的安装回执匹配后，在持锁期间重新核对哈希并回收冗余备份。信任存储不可用或校验不通过时保留。

## 1. 签名与来源信任

在 v1 无 OS 沙箱的前提下(见 06/12),"用户装了什么、来自谁"是安全
模型的支柱,因此签名从第一版就是**强制**的。

方案:**开发者密钥签名 + 首次信任(TOFU)+ 官方源背书**,分三档:

| 信任档 | 含义 | UI 表现 |
| --- | --- | --- |
| 官方插件 | VelaShell 团队密钥签名 | 蓝标"官方" |
| 已验证发布者 | 密钥在官方源注册且通过发布者验证(GitHub 账号绑定等轻量验证) | 绿标"已验证:acme" |
| 未验证 | 有效自签名但发布者未注册 | 黄标警示;安装需二次确认("仅在信任来源时安装") |

机制:

- 签名格式:对包内全部文件的 SHA-256 清单(`SIGNATURE` 内含 manifest
  hash 树 + Ed25519 签名 + 公钥 + 可选官方源反签)。
- 无签名/签名损坏的包**拒绝安装**(开发模式 dev 装载除外,UI 明示 DEV)。
- **同 id 升级必须同公钥**(密钥连续性,防更新劫持);换钥需官方源
  背书流转。
- 宿主内置官方源根公钥;吊销列表随源索引下发(被吊销发布者的已装插件
  标红并默认禁用)。

## 2. 安装与更新管线

```text
来源(文件/URL/源页面)→ 下载到临时目录 → zip 安全解包(防 zip-slip)
 → 签名校验 → manifest 校验(schema/engines/platform/权限清单)
 → 权限预览页(逐条展示,危险权限红标;升级时高亮"新增权限")
 → 用户确认 → 落盘 installed/<id>/<ver>/ → 注册贡献点 → 完成(免重启)
```

- 更新检查:后台按源索引对比版本(默认每日;可关);更新沿用 03 §7
  的原子版本指针切换,失败回滚。
- 自动更新默认**关**(运维工具的保守取向:目标机器上意外变更是事故
  源);提供"仅安全更新自动装"(源索引标记 security 位)选项。
- 降级:管理页允许回退到本机缓存的上一版本(排障出口)。

## 3. 插件源(Registry)

分阶段,避免过早自己架服务:

**阶段 A(v1)——静态索引源**:一个托管在 GitHub(Pages/Release)的
签名 JSON 索引,宿主可配置多个源(企业内网可自己部署同格式源,满足内网
分发场景):

```jsonc
// index.json(整体带官方签名)
{ "version": 1, "generatedAt": "...",
  "plugins": [ { "id": "acme.image-viewer", "latest": "1.2.0",
      "versions": [ { "version": "1.2.0", "engines": {"velaShell": ">=0.2.0", "apiLevel": 1},
          "url": "https://.../image-viewer-1.2.0.vpx", "sha256": "...",
          "publisherKey": "ed25519:...", "permissions": ["remote.files.read"],
          "security": false } ],
      "displayName": {"en": "...", "zh-Hans": "..."}, "description": {...},
      "icon": "https://...", "verifiedPublisher": true } ],
  "revokedPublishers": ["ed25519:..."] }
```

> 现状（2026-10-25）：应用内插件更新只走 https，商店的下载票据必须给出包的 `fileSha256`（64 位十六进制），缺了或商店 / 下载地址是 http 就在发下载请求之前拒绝；下好之后核对摘要，安装时照旧验签。

**阶段 B——官方市场**:动态服务(搜索、下载计数、评分、发布者门户、
自动扫描),仅当生态起量再投入;索引格式向前兼容阶段 A。

## 4. 应用内插件管理页

**当前实现：** 插件管理窗口分为「已安装」和「插件商店」。已安装卡片将信息与操作分行，操作按钮可换行；商店采用列表与详情分栏，支持搜索、排序、分页及安装/更新，底部统一显示进度与取消入口。离线错误与空列表分开呈现，可重试；保留本地包安装。页面文案使用五语言 resx，插件自述按服务端原文显示。

**以下仍是长期蓝图，不代表全部已经实现：**

- **已安装**:卡片列表(图标/名称/发布者信任标/版本/状态色点);行内
  操作:启用/禁用/卸载/重启/查看日志;展开:权限、最近活动(审计)、
  资源占用(内存曲线)、不体面退出计数。
- **浏览**:聚合各配置源的索引,搜索/分类;详情页 = README 渲染 +
  权限清单 + 版本历史。
- **状态可视**:Faulted 红、无响应黄、运行绿、未激活灰——与 04 状态机
  一一对应。
- 五语言:页面文案入现有 resx 五语平价流程;插件自述文案用源索引的
  多语言字段,缺失回退英文。
